# 249 — Distribution: Sparkle 2 integration (phase A3)

Wires Sparkle 2 auto-update into the sandboxed AtelierRefs app, per the 052
distribution plan's **A3** phase (decisions **1A** Developer ID + Sparkle channel,
**2A** sandboxed XPC integration, **5A** EdDSA key in Keychain).

## Summary

- Added **Sparkle 2** as a remote SPM dependency (`https://github.com/sparkle-project/Sparkle`,
  `upToNextMajorVersion` from `2.6.0`; resolved to **2.9.4**). The binary
  XCFramework bundles the **Downloader** (`org.sparkle-project.DownloaderService`)
  and **Installer** (`org.sparkle-project.InstallerLauncher`) XPC services plus
  `Updater.app` inside `Sparkle.framework`, so linking the SPM product embeds them
  automatically — no separate Copy-Files phase is needed (verified: the built
  `.app` carries `Contents/Frameworks/Sparkle.framework/.../XPCServices/{Downloader,Installer}.xpc`).
- **Sandboxed integration (2A):** the app keeps app-sandbox, hardened runtime,
  `network.server`, `network.client`, and `files.user-selected.read-write`. Added
  only the two mach-lookup temporary-exception entitlements Sparkle's sandboxing
  guide requires; enabled the Installer launcher XPC service via Info.plist.
- **Updater controller + menu command:** an app-global `SPUStandardUpdaterController`
  (`startingUpdater: true`) with a "Check for Updates…" command under
  `CommandGroup(after: .appInfo)`, its enabled state tracking `canCheckForUpdates`.
- **Release scripts:** replaced the A2 `TODO(A3)` guards in `release.sh`
  (`generate_appcast`) and `verify-release.sh` (`sign_update`) with working
  invocations + auto-discovery of `SPARKLE_BIN_DIR`.

## The exact keys added

Entitlements (host app):
```
com.apple.security.temporary-exception.mach-lookup.global-name = [
    $(PRODUCT_BUNDLE_IDENTIFIER)-spks,
    $(PRODUCT_BUNDLE_IDENTIFIER)-spki,
]
```
Info.plist:
```
SUFeedURL                        = https://REPLACE-ME.example.com/atelierrefs/appcast.xml   (PLACEHOLDER)
SUPublicEDKey                    = REPLACE_WITH_PUBLIC_ED_KEY_FROM_generate_keys            (PLACEHOLDER)
SUEnableInstallerLauncherService = YES
```
The Downloader XPC service is intentionally NOT enabled (`SUEnableDownloaderService`
omitted): the app retains `network.client`, so Sparkle downloads in-process.

## Verification done

- `swift package resolve` / `xcodebuild -resolvePackageDependencies`: Sparkle 2.9.4
  resolves alongside the local packages.
- **Unsigned build** (`CODE_SIGNING_ALLOWED=NO`, Debug): **BUILD SUCCEEDED**. The
  Swift updater code compiles and links `-framework Sparkle`; Sparkle.framework +
  both XPC services embed into the built `.app`; the merged Info.plist carries all
  three Sparkle keys.
- Real `SPARKLE_BIN_DIR` (auto-discovery target):
  `~/Library/Developer/Xcode/DerivedData/AtelierRefs-<hash>/SourcePackages/artifacts/sparkle/Sparkle/bin`.

## Migration / required human steps (still BLOCKED on a person)

1. **Generate the EdDSA keypair** once on the release machine:
   `"$SPARKLE_BIN_DIR/generate_keys"` (private key → login Keychain, 5A), then paste
   the printed public key into `SUPublicEDKey`, replacing the placeholder.
2. **Decide appcast/DMG hosting** (052 "Open questions") and set the real
   `SUFeedURL`, replacing the `REPLACE-ME.example.com` placeholder.
3. **A4 config-contract test** will assert both values are non-placeholder — a
   build shipping either placeholder fails the guard by design.
